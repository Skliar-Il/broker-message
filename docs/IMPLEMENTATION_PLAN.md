# План реализации broker-message

Этапы и зависимости между ними.

---

## Фаза A — Ядро и MQTT (MVP)

1. **Внутреннее ядро**  
   - Badger: каталог данных; ключи журнала `topic + seq`.  
   - Создание, удаление и метаданные топиков и очередей.  
   - `Publish`, `Subscribe`, FIFO, несколько подписчиков (fan-out).

2. **MQTT**  
   - TCP: `CONNECT`, `PUBLISH`, `SUBSCRIBE`, `UNSUBSCRIBE`, `PING`, `DISCONNECT`.  
   - Старт с QoS 0; затем QoS 1 для персистентной доставки.

3. **Тесты** — юнит-тесты ядра, интеграционные сценарии.

**Готовность:** публикация и приём из двух клиентов; несколько подписчиков получают сообщения.

---

## Фаза B — Docker и демо

1. Dockerfile для брокера.  
2. `docker-compose.yml`: брокер, volume для Badger, порты, переменные окружения.  
3. Три микросервиса: публикатор с логом, подписчик с логом, третий сервис (второй подписчик или агрегатор).  
4. Скрипт или Makefile для запуска демо.  
5. `docs/BUILD.md` — сборка `GOOS`/`GOARCH`, примеры мультиархитектурных образов.

**Готовность:** `docker-compose up` поднимает брокер и три сервиса; по логам виден полный сценарий.

---

## Фаза C — Персистентность и гарантия доставки

1. Запись в Badger согласованно с подтверждениями издателю.  
2. QoS 1: packet id, PUBACK, повторы, дедупликация на клиенте.  
3. Смещения подписчиков и незавершённые доставки в Badger.  
4. Тест: рестарт брокера — сообщения и состояние доставки согласованы с QoS.

---

## Фаза D — SDK

1. Пакет `sdk/`: `Connect`, `Publish`, `Subscribe` с контекстами.  
2. Типизированные ошибки (сеть vs протокол).  
3. Переподключение: backoff, восстановление подписок.  
4. Примеры в `examples/`.

---

## Фаза E — Документация

1. Актуальный README (запуск, compose, переменные).  
2. Обновление `docs/ARCHITECTURE.md`.  
3. Godoc для SDK; при HTTP API — OpenAPI или `docs/API.md`.  
4. Диаграммы (Mermaid в репозитории или экспорт в изображения).

---

## Фаза F — TTL

1. Поле `expires_at` в метаданных или соглашение в протоколе — зафиксировать в документации.  
2. Не выдавать просроченные сообщения; фоновая очистка в Badger.

---

## Фаза G — DLQ

1. Политика переноса после N неудач или по флагу.  
2. Хранение в Badger отдельным префиксом; подписка на DLQ для разбора.

---

## Фаза H — Метрики Prometheus

1. HTTP endpoint `/metrics`.  
2. Счётчики: входящие/исходящие сообщения, ошибки, бэклог, активные клиенты.

---

## Фаза I — Аутентификация и авторизация

1. Username/password в MQTT `CONNECT`.  
2. ACL по префиксам топиков (конфиг или Badger).

---

## Фаза J — Web UI

1. HTTP-интерфейс: статус, топики, глубина очередей, ссылка на метрики.  
2. При необходимости — простые графики или ссылка на внешний дашборд.

---

## Рекомендуемый порядок работ

1. Фазы **A** и **B** — работающий продукт в контейнерах с демо.  
2. Затем **C**, **D**, **E**.  
3. После этого **F** → **G** → **H** → **I** → **J**.

---

## Упрощения

- Один узел брокера без кластера.  
- QoS 2 — по необходимости после QoS 1.  
- Web UI можно начать с JSON API и ссылки на Prometheus, затем расширить интерфейс.
