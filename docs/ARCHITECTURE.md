# Архитектура broker-message

Документ фиксирует границы модулей и потоки данных. По мере реализации сюда добавляются диаграммы последовательностей и ссылки на API.

**Диаграмма (draw.io):** [broker-architecture.drawio](broker-architecture.drawio) — ядро с вложенным буфером RAM, потоки PUBLISH / DELIVER из буфера в адаптер.

## Модули (план)

| Модуль | Ответственность |
|--------|-----------------|
| `cmd/broker` | Точка входа: конфиг, флаги, запуск MQTT и фоновых задач |
| Внутреннее ядро | Реестр топиков/очередей (создание, удаление, метаданные), назначение `seq`, FIFO, fan-out подписчикам. **Включает буфер RAM**: логика ядра пишет в буфер и при доставке подписчикам читает из него |
| Буфер RAM | Часть ядра: горячий хвост сообщений для низкой задержки; **исходящие к подписчикам** формируются из буфера и передаются в MQTT-адаптер |
| Адаптер MQTT | Декодирование пакетов, сессии клиентов; приём входящего трафика в ядро и **отправка исходящего из буфера ядра** к клиентам |
| Хранилище (Badger) | Журнал сообщений, смещения подписчиков, данные для восстановления, метаданные TTL/DLQ |
| Метрики | Prometheus `/metrics`, счётчики публикаций, ошибок, размеров очередей |
| Auth | Проверка учётных данных MQTT, ACL по топикам |
| Web UI | HTTP: статус, топики, очереди, ссылка на метрики |

## Поток публикации

1. Клиент отправляет MQTT `PUBLISH`.
2. Адаптер валидирует сессию и права (если включена авторизация) и передаёт данные **в ядро**.
3. Логика ядра присваивает `seq`, при необходимости выставляет `expires_at` (TTL), **записывает в буфер RAM** (часть ядра) и в Badger (политика fsync зависит от QoS).

## Поток доставки подписчикам

1. `SUBSCRIBE` регистрирует фильтр в ядре и привязывает к сессии адаптера.
2. При появлении сообщений для подписчика **ядро читает из буфера RAM** (при необходимости догружая хвост с Badger) и передаёт кадры **в MQTT-адаптер**, адаптер отправляет их клиентам.
3. Учёт последнего подтверждённого offset (QoS 1) согласован с записями в Badger.
4. Сообщения, не подлежащие повторной доставке или просроченные по TTL, не отдаются из буфера или помечаются для DLQ по политике.

## Сбой и восстановление

- При рестарте процесса Badger поднимается с тем же каталогом данных.
- Восстанавливаются метаданные топиков/очередей и смещения; незавершённые QoS 1 доставки дообрабатываются согласно спецификации MQTT.

## DLQ

- Отдельный префикс ключей или топик `…/dlq`; правила переноса задаются политикой брокера.
